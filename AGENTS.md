# Инструкции для AI-агентов

Logistics Company — учебный проект команды из четырёх разработчиков. Четыре контрольные работы последовательно развивают одну предметную область и одну базу данных. Текущая фаза — подготовка структуры, начало КР1; наличие каталога не означает, что компонент реализован.

## Перед каждой новой задачей

Сначала прочитай файлы в следующем порядке:

1. `AGENTS.md`
2. `docs/PROJECT_CONTEXT.md`
3. `docs/REQUIREMENTS.md`
4. `docs/ARCHITECTURE.md`
5. `docs/ROADMAP.md`
6. `docs/DECISIONS.md`
7. `docs/TASKS.md`

Затем прочитай README затрагиваемого компонента и относящиеся к задаче документы. Установи, к какой КР относится запрос, какие возможности уже существуют и что разрешено менять. Явные инструкции пользователя определяют объём текущей задачи. Не реализуй будущие КР заранее.

До изменений проверь структуру, текущую ветку, `git status` и существующую конфигурацию сборки. Сохраняй рабочий код, настройки и пользовательские изменения; не включай чужие изменения в свои коммиты.

## Архитектурные границы

- Корневой Java package: `com.logisticscompany`; не используй `ru.mirea` и другие названия университета.
- КР1: Console UI → Service → Repository/JDBC → PostgreSQL.
- КР2: отдельный JavaFX-клиент, FXML/View → Controller → Service → Repository/DAO/JDBC → PostgreSQL. Он обращается к БД напрямую через JDBC и не зависит от REST backend КР3.
- КР3: REST Controller → Spring Service → Spring Data JPA → PostgreSQL. Развитие схемы через Flyway, Hibernate `ddl-auto: validate`.
- КР4: Android на Java с source compatibility 17 → HTTP/REST → backend КР3 → PostgreSQL. Android никогда не подключается напрямую к PostgreSQL.
- Начиная с КР3 клиенты используют REST там, где это предусмотрено требованиями. Появление backend само по себе не меняет архитектуру JavaFX КР2.
- Не смешивай UI, Service и Repository. SQL не должен находиться в UI; бизнес-правила принадлежат сервисному слою.
- Не дублируй бизнес-логику. При необходимости переиспользования сначала оцени существующие границы модулей и зафиксируй решение; не создавай общую библиотеку заранее.
- Не добавляй новые библиотеки и зависимости без необходимости текущей задачи.
- Не создавай отдельный SPA frontend без отдельного запроса. Возможный web-интерфейс КР3 размещается в `backend/src/main/resources/static/`.

На этапе foundation разрешены структура, документация, безопасные шаблоны и маркеры каталогов. Не добавляй сущности, SQL, CRUD, JDBC-реализации, UI, Spring Boot/Security, миграции, Docker Compose или Android Gradle-проект. Уже существующие файлы сохраняй.

## Изменения и Git

- Не работай непосредственно в `main`. Используй отдельную ветку для одной задачи: `feature/*`, `fix/*`, `refactor/*`, `chore/*`, `docs/*` или `test/*`.
- Делай небольшие логические коммиты в формате Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`. Отделяй перенос файлов от содержательных изменений.
- Не меняй несвязанный код, не выполняй массовое форматирование и не удаляй чужие файлы без необходимости.
- Не используй `git reset --hard`, `git clean -fd`, force push в общие ветки или rebase с переписыванием чужой истории.
- Пользователь разрешил обычный push проверенных коммитов в рабочую ветку задачи на GitHub без повторного запроса. Прямой push в `main` по-прежнему запрещён; не отправляй изменения в другие ветки без необходимости задачи.
- Создание Pull Request (включая draft PR) и merge пользователь выполняет сам. Агент выполняет каждое из этих действий только по отдельной явной просьбе пользователя; разрешение на push не разрешает PR или merge.
- Перед коммитом запускай доступные релевантные тесты и проверку сборки. При недоступных инструментах укажи точную причину и не объявляй проверку успешной.
- Проверяй staged diff перед коммитом и состав коммита после него. Не добавляй секреты, `.env`, локальные IDE-файлы или результаты сборки.
- При архитектурных изменениях обновляй документацию, `docs/DECISIONS.md` и затронутые задачи в `docs/TASKS.md`.

## Сборка и завершение задачи

Рабочая Maven-структура пока находится в корне (`pom.xml`, `src/`); `console-app/` обозначает будущий отдельный модуль. Не переноси её без проверки безопасности. Базовая команда проверки из корня: `mvn -B test`; подробности и ограничения среды см. в `docs/DEVELOPMENT.md`.

В отчёте укажи ветку, изменения, выполненные проверки и их фактические результаты, созданные коммиты и итоговый `git status`. Отделяй реализованное от запланированного. После foundation остановись: следующая задача должна отдельно разрешить реализацию КР1.
