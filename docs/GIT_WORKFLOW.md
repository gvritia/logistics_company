# Командный Git workflow

В проекте четыре разработчика. `main` должен всегда оставаться рабочим. Все изменения проходят через отдельную ветку и Pull Request; прямые изменения `main` запрещены.

## Ветки

| Ветка | Назначение |
| --- | --- |
| `main` | Согласованное рабочее состояние проекта |
| `feature/*` | Новая функциональность текущей КР |
| `fix/*` | Исправления ошибок |
| `refactor/*` | Изменение структуры без изменения поведения |
| `chore/*` | Конфигурация, инструменты, структура проекта |
| `docs/*` | Документация |
| `test/*` | Самостоятельные задачи по тестированию |

Одна задача — одна ветка. Хорошие названия:

```text
feature/transportation-request-model
feature/client-repository
feature/request-search
fix/request-validation
chore/project-foundation
docs/update-architecture
```

Если имя занято, используйте осмысленный суффикс; не заменяйте существующую ветку. Префикс, добавленный инструментом, допустим, если название сохраняет назначение задачи.

## Начало и обновление работы

Сначала проверьте `git status` и текущую ветку. Не переносите и не включайте чужие локальные изменения в свою задачу. Следующий пример рассчитан на чистое рабочее дерево и настроенный remote `origin`:

```bash
git fetch origin
git switch -c feature/transportation-request-model origin/main
```

Перед PR и после значимых изменений `main` получите актуальное состояние через `git fetch origin`. Обновляйте рабочую ветку от актуального `origin/main`, сохраняя общую историю. Для общей ветки подходящим способом является merge `origin/main` в ветку задачи по согласованному процессу команды. Разрешайте конфликты в ветке задачи до merge PR и повторяйте затронутые проверки.

Не используйте rebase с переписыванием чужой истории. Не делайте force push в общие ветки. Не используйте `git reset --hard` или `git clean -fd` для устранения локальных проблем.

## Коммиты

Коммит решает одну понятную задачу. Не смешивайте перенос файлов, изменение поведения и несвязанную документацию. Используйте Conventional Commits:

```text
feat: add transportation request model
fix: validate request weight
refactor: move console application into dedicated module
docs: describe database evolution
test: cover request status transitions
chore: establish project foundation
```

Эти примеры функциональности относятся к будущим задачам, а не к текущему foundation.

Перед коммитом запускайте доступные проверки и просматривайте staged diff. Добавляйте файлы выборочно, если в рабочем дереве есть несвязанные изменения. После коммита проверьте `git show --stat --oneline HEAD` и `git status --short`.

## Pull Request и review

- PR должен быть небольшим и относиться к одной задаче. Укажите КР, причину изменений и ожидаемый результат.
- Заполните [шаблон PR](../.github/pull_request_template.md), включая фактические результаты проверки сборки и тестов.
- Не смешивайте задачи разных участников и несвязанные исправления в одном PR.
- Обновите ветку от актуального `main` и разрешите конфликты до merge.
- Получите review другого участника. Если обязательное review настроено в GitHub, перед merge необходим минимум один одобряющий review.
- Обсудите замечания и внесите исправления. `main` после merge должен оставаться рабочим.
- После merge удалите завершённую feature-ветку, убедившись, что в ней нет несохранённой работы.

Этот документ описывает процесс команды, но не настраивает защиту веток в GitHub. Её фактическое состояние проверяется отдельно.

## Публикация веток и работа агентов

Пользователь разрешил AI-агенту обычный push проверенных коммитов в рабочие ветки задач на GitHub без повторного запроса. Перед push агент проверяет ветку, remote, состав коммитов и результаты доступных проверок. Прямые изменения и push в `main` остаются запрещены; force push в общие ветки недопустим.

Pull Request (в том числе draft PR) создаёт пользователь, merge также выполняет пользователь. Агент может выполнить любое из этих действий только по отдельной явной просьбе пользователя. Разрешение на push не является разрешением создавать PR или выполнять merge.

После push агент сообщает название опубликованной ветки и результат проверки публикации. Правила review и сохранения рабочей `main` остаются частью командного процесса.
