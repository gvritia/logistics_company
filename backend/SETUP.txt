КР3: первый запуск backend

Требуются Docker Desktop, JDK 21 и Maven 3.9 для локальной сборки.
Корневой .env должен содержать POSTGRES_DB, POSTGRES_USER,
POSTGRES_PASSWORD, JWT_SECRET_BASE64, BOOTSTRAP_ADMIN_EMAIL и
BOOTSTRAP_ADMIN_PASSWORD. Пример без секретов — в .env.example.
Для JWT_SECRET_BASE64 нужен случайный ключ (не менее 32 байт). Например,
в PowerShell его можно получить командой:

  [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))

Вставьте результат в локальный .env. Задайте уникальный пароль администратора
длиной от 12 до 72 байт UTF-8. Файл .env игнорируется Git. При первом запуске
на пустой базе создаётся только ADMIN с обязательной сменой пароля.

Из корня репозитория в PowerShell:

  powershell -ExecutionPolicy Bypass -File .\backend\start-compose.ps1

Скрипт собирает backend и запускает PostgreSQL 17 и Spring Boot в Docker.
Compose КР3 использует отдельные проект и том `logistics-kr3`. Он не меняет
том и данные Compose КР2. В пустой базе Flyway автоматически выполняет V1,
V2 и V3. Проверка:

  http://localhost:8080/api/system/info
  http://localhost:8080/actuator/health
  http://localhost:8080/docs-login.html
  http://localhost:8080/swagger-ui.html
  http://localhost:8080/v3/api-docs

PostgreSQL КР3 опубликован только на 127.0.0.1:55433; backend — только на
127.0.0.1:8080. Порты можно изменить через KR3_POSTGRES_PORT и APP_PORT.

Авторизация доступна через POST /api/auth/login. Тело JSON:

  {"email":"адрес из BOOTSTRAP_ADMIN_EMAIL","password":"пароль из .env"}

Ответ содержит accessToken (JWT, по умолчанию 15 минут), refreshToken
(по умолчанию 14 дней) и признак passwordChangeRequired. Передайте JWT как
Authorization: Bearer <accessToken>. Временный пароль меняется через
POST /api/auth/change-password с полями currentPassword и newPassword.
После смены все прежние токены недействительны: выполните вход заново.
POST /api/auth/refresh меняет refresh-токен на новую пару; старый токен
повторно использовать нельзя. POST /api/auth/logout отзывает refresh-токен.
GET /api/auth/me возвращает текущего пользователя.

Swagger и остальные служебные маршруты доступны только ADMIN после смены
пароля. Откройте /docs-login.html в браузере, введите ADMIN email и пароль
из локального .env. При временном пароле форма предложит сменить его.
После входа короткая HttpOnly cookie откроет Swagger в том же браузере.
На странице входа также показан access JWT: скопируйте его, откройте Swagger
по ссылке в новой вкладке, нажмите Authorize и вставьте JWT. В поле Swagger
достаточно самого токена, без слова Bearer. После истечения JWT войдите снова.
Основное API принимает JWT только из заголовка Authorization. Пароли и
refresh-токены не сохраняйте в браузерном localStorage. Для доступа вне
localhost используйте HTTPS и COOKIE_SECURE=true. Лимиты входа: 20 попыток
за 5 минут с одного IP и блокировка учётной записи на 15 минут после пяти
ошибок. Не доверяйте произвольному X-Forwarded-For при публикации за прокси.

Полный web-интерфейс будет добавлен следующим этапом. Hibernate использует
ddl-auto: validate.

Заявки: GET /api/requests, GET /api/requests/{id},
POST /api/requests, PUT /api/requests/{id}, DELETE /api/requests/{id},
POST /api/requests/{id}/restore. Идентификатор {id} — UUID; числовой id
остаётся внутренним ключом БД. Запись создаётся в статусе CREATED и без
доставщика. Редактируется только активная заявка в статусе CREATED.
PUT передаёт version в JSON. Архив и восстановление передают ожидаемую
version параметром URL; неверная версия возвращает 409. VIEWER читает,
EDITOR и ADMIN меняют. GET /api/clients, /api/operators и /api/drivers
дают данные для формы. Справочники могут быть пустыми в новой БД.

Справочник клиентов: GET /api/clients (необязательный фильтр active=true/false),
GET /api/clients/{id} доступны авторизованным пользователям. Только ADMIN
может вызвать POST /api/clients с fullName, phone и/или email, PUT
/api/clients/{id} с теми же полями и ожидаемой version, POST
/api/clients/{id}/activate?version=... и /deactivate?version=.... Нужен
хотя бы один контакт. Клиент с заявками сохраняется в справочнике после
отключения; для новой заявки его выбрать нельзя. Конфликт версии даёт 409.
Ключ клиента остаётся числовым для совместимости с КР1/КР2.

DELETE /api/requests/{id}/permanent доступен только ADMIN для архивной
заявки и по умолчанию отключён. Для разрешения укажите
PERMANENT_DELETE_ENABLED=true в локальном .env и перезапустите backend.
Физическое удаление необратимо; для обычной работы используйте архив.
GET /api/requests принимает q (текст по коду, грузу, адресам и клиенту),
clientId, status, fragile, weightCategory, tag, archived, weightOp,
weightValue, page, size и sort. По умолчанию archived=false, page=0,
size=20, sort=createdAt,desc. Размер страницы — не более 50. sort задаётся
в форме поле,направление; разрешены createdAt, plannedDeliveryAt, price,
weightKg и requestCode, направления asc/desc. weightOp вместе с weightValue:
eq, lt, lte, gt, gte. Значения weightCategory: LIGHT (меньше 1000 кг),
MEDIUM (от 1000 до 5000 кг), HEAVY (от 5000 кг). Фильтры сочетаются по AND.
Символы % и _ в текстовом поиске считаются обычными символами.

Пример: GET /api/requests?status=APPROVED&fragile=true&sort=price,desc

Процесс перевозки: POST /api/requests/{id}/approve, /cancel, /unassign,
/start и /deliver принимают ожидаемую version параметром URL. POST
/api/requests/{id}/assign принимает JSON {"driverId": 1, "version": 0}.
Нужна роль EDITOR или ADMIN. Переходы: CREATED → APPROVED/CANCELLED,
APPROVED → IN_TRANSIT/CANCELLED, IN_TRANSIT → DELIVERED. Назначить можно
только активного доставщика на свободную APPROVED-заявку; снять его можно
до начала перевозки. Для START и DELIVER доставщик должен быть назначен.
Архивную заявку сначала восстановите. Недопустимый переход или устаревшая
version возвращает 409. Каждое успешное действие записывается в аудит.

Заметки заявки: GET /api/requests/{id}/notes возвращает историю, сначала
закреплённые, затем новые. POST /api/requests/{id}/notes принимает JSON
{"body":"Текст заметки","pinned":false}; ответ содержит UUID, автора,
время создания/изменения и version. PUT /api/requests/{id}/notes/{noteId}
принимает body, pinned и ожидаемую version. DELETE по этому же адресу
принимает version параметром URL. Читать может VIEWER, писать — EDITOR и
ADMIN; EDITOR меняет и удаляет только свои заметки, ADMIN — любые.
У архивной заявки заметки доступны для чтения, но не для изменений.
Старая версия даёт 409, отсутствие заявки/заметки — 404.

Массовые операции: POST /api/requests/bulk для EDITOR и ADMIN. Пример:

  {"action":"ADD_TAG","tag":"priority","items":[{"id":"UUID","version":0}]}

За один запрос — от 1 до 100 разных UUID с ожидаемой version у каждого.
Действия: ARCHIVE, RESTORE, CHANGE_STATUS (поле status: APPROVED,
CANCELLED, IN_TRANSIT или DELIVERED), ADD_TAG и REMOVE_TAG (поле tag).
Правила переходов и архива те же, что у одиночных операций. Каждый элемент
обрабатывается отдельно: успешные изменения сохраняются, даже если другой
элемент не прошёл проверку. Ответ содержит succeeded, failed, successes
(id, version, status, archived) и failures (id, code, message). Дубли UUID
и неверная комбинация action/status/tag дают 400 для всего запроса.

CSV и web-интерфейс — следующие части.

Существующую БД КР1/КР2 переводите по инструкции MIGRATIONS.txt после
резервной копии. Автоматический baseline отключён. Для остановки без удаления
данных:

  powershell -ExecutionPolicy Bypass -File .\backend\stop-compose.ps1

Команда docker compose down без -v сохраняет том PostgreSQL.
